02Abstract

A recommendation request on Reddit draws several replies, each naming different titles. When an LLM recommender is trained on such threads with reinforcement learning (RL), which replies should a generated list be rewarded against? The state-of-the-art recipe, Rank-GRPO, picks one reply per training example, so the advantage mostly records which reply was drawn (85% of its variance) rather than how good the list is.

We argue that RL should train on the request, not on each answer, and propose ReMaRk: it scores every list once against the union of all replies' titles and samples each request equally. This makes RL cheaper. On seven backbones and three datasets, ReMaRk reaches the validation recall of 2,000 per-reply RL steps in 25 to 53% of the steps and leads at that budget; trained until neither improves, it is never significantly behind Rank-GRPO and in four of seven pairs reaches Rank-GRPO's best with fewer GPU-hours.

The same reward helps on ProtoQA, where about 100 people answer each question, which points to a simple rule for RL with several valid human answers: reward them jointly.

03Method

One row per request, one reward against all responders.

Rank-GRPO turns each responder into a separate training row and rewards a list only for that responder's titles. ReMaRk keeps the online GRPO update and changes only the training unit.

Rank-GRPOOne row per responder
  • Rank-GRPO. A list earns rank-level credit for every title the one drawn responder named; requests with more responders are drawn more often.
  • The problem. Responders rarely agree: most suggested titles are named by a single person, so a good list scores high or low depending on who was drawn.
ReMaRkOne row per request
  • Union reward. Each position of a list earns 0/1 credit if any responder of the request named that title.
  • Request sampling. Every request is drawn equally, once instead of once per responder; per-group advantage scaling stays bounded for 0/1 rewards.

04Why it works

The responder is a nuisance variable.

Which responder ends up in a training row is an accident of how the data were collected. Averaging the reward over the responders is a Rao–Blackwellization: at a fixed advantage scale the expected update is unchanged and a variance term disappears. GRPO's per-group scaling can amplify one responder's vote when rewards are fractional, so ReMaRk keeps a 0/1 reward on the union, whose scale stays bounded.

  • The gain follows the variance removed. It grows with the number of responders and with the share of responder noise removed.
  • Pooling matters, not the aggregate. Once list lengths are controlled, the averaged reward is level with the union at 2B.
  • Same end point, reached sooner. Lower variance predicts faster progress, so we measure the RL compute needed to reach a target.

05Results

What the experiments show.

R1 · COMPUTE

The same recall with less RL compute.

Best validation recall so far against training GPU-hours for pairs trained until neither improves. Trained this long, ReMaRk is never significantly behind on test, and in four of seven pairs it reaches Rank-GRPO's best with 18 to 63% of the GPU-hours.

Where it does not help. On requests with a single responder every aggregation equals the per-responder reward, so on datasets with one recommender per request ReMaRk reduces to Rank-GRPO. Its value grows with the share of requests that have several responders.

R2 · EVERY SETTING

A lead in every setting.

Test gain over the better per-responder baseline at 2,000 steps, with 95% confidence intervals, for every backbone, dataset and seed.

R3 · NOISE REMOVED

The gain follows the responder noise removed.
